From a minute to a second: where the time to build t27 went, and where it still goes

2026-10-11 · 11 min read

[measured on one 8-core Mac whose load varied overnight; pairs taken under the same load] One overnight loop measured every place t27 builds and waits, and fixed what the numbers pointed at. A warm t27c frontier went from 55-68 s to about 0.9 s, an unchanged bitstream is found in 0.22-0.39 s instead of 4.3-8.9 s, a board run after approval no longer builds first, and the corpus suite CI runs on every pull request dropped from 221-257 s to 108-140 s. Almost all of the old time went into recomputing what had not changed and into running independent work one item at a time. What is left: about 2 s per spec in zig's relink, 27 s of nextpnr per logic change, about 14 s to load a board, and a 72 s C-header gate. Each speed-up is now one `tri hot` command, recorded before and after, and set against eight build tools in a TOP.

#t27#Measurement#FPGA#Verification

Overnight from 10 to 11 October, one loop went through every place t27 builds something and makes its author wait, measured each one, and changed what the measurements pointed at. A warm t27c frontier went from about a minute to under a second, a bitstream that has not changed is found in a quarter of a second instead of four to nine, and the corpus suite that CI runs on every pull request takes half its old time. Thirteen pull requests, all merged; the record is the loop ledger, t27#8737.

Where the time went

Almost none of it went into work that was new. It went into recomputing what had not changed since the last run, and into doing independent pieces of work one after another. Every fix below is one of those two.

Three rules did most of the work

  1. Key a cache on everything that can change the output, and on nothing else. The generated code of a spec depends on its imports, because constants are inlined across them, so the key holds the whole import closure. It also holds the binary itself: any rebuild of t27c is a new generator. A key that names too little serves wrong answers; a key that names too much, like a commit of an unrelated checkout, throws good answers away.
  2. Check something cheap before something expensive. A file stat costs microseconds; reading and hashing 333 MB costs seconds. The watch and the digest cache both look at the stat first and read only what moved, and they take the stat before reading, so an edit that lands during a read is seen next time.
  3. Run independent work side by side, and prove it changed nothing. Every parallel phase folds its results in input order, and each one was run both ways, with T27_SUITE_JOBS=1 and with the default: the error output was byte-identical, the JSON summaries equal apart from their timing fields, 259 failures both times.

Defects found on the way

  • The bitstream cache key held pip freeze, which named the editable prjxray package by the commit of the t27 checkout around it. A commit there would have orphaned every cached bitstream, while an edit to prjxray itself never reached the key (t27#8814).
  • When the bench agent stopped a build that ran past its hour, yosys and nextpnr kept running under launchd. Its timeout now stops the whole process tree (t27#8819).
  • The first version of the watch spent a third of a core doing nothing (t27#8825).
  • The new tri hot read its first silicon measurement as OVER, 28 s on a healthy cache: every tenth reuse hit is rebuilt from scratch on purpose, as an audit of the key, and that run had been timed. It now times such a run once more (t27#8872).

Every speed-up as one command, before and after

Each speed-up above is now one tri hot word (t27#8953): watch, frontier, prebuild, suite and caches, with tri hot alone as the check. Below, each one was recorded twice on this Mac on 11 October: before, with the speed-up switched off by the same knob used to verify it, and after. The typing is staged; every byte printed is real and arrives when it was printed. time prints the real duration.

Against the field: the TOP

Six things this post needs, a spec’s verdict and then its bitstream on a board, checked against each tool’s own documentation. Yes means the tool does it; half means partly, or only with a separate tool or by wrapping the flow; no means it does not, or the documentation checked does not say so.

Score53.53331½½½
  1. t27 tri hot, 5 of 6. What it lacks is a shared cache: every machine builds its own, and the shared-bitstream path (P8) is a spec, not a service.
  2. Bazel, 3.5: cached test results and a remote cache; a watch only through ibazel, and disk-cache garbage collection still experimental.
  3. Nx, Gradle and Nix, 3 each. Nx and Gradle cache tasks and rerun on change; Nix shares binary caches and can rebuild a path to check that it is deterministic.
  4. ccache, 1: a bounded compiler cache, and nothing above the compiler.
  5. Vivado incremental, Quartus Rapid Recompile and LiteX, half each. Vivado reuses placement and routing from a reference checkpoint but still runs them; Quartus reuses fitting for a change it judges small, and the Pro edition removed it in 21.1; LiteX reloads firmware without rebuilding the gateware. None skips a build whose inputs did not change.

This TOP is weighted toward this workflow: its rows are the six things t27 needed. On remote execution, ecosystem and scale, which is what a general build system is chosen for, Bazel, Nx, Gradle and Nix are far ahead, and t27 has no shared cache at all. No competitor was run on this workload; every number in this post is t27’s own, measured on one Mac.

What this does not settle

  • No board run was made after these changes: the ~13-15 s board load is from earlier runs, and the faster JTAG clock is untested.
  • All timings come from one Mac whose load varied from about 3 to about 140; the pairs were taken under the same load, but an idle-machine run of the whole flow is still owed.
  • The nextpnr patch is measured on two designs only (byte-identical output on both); it is not upstream and not in the toolchain the bench uses.
  • Skipping the per-run zig relink would cut a verdict to about 0.2-0.3 s, but it changes the test runner every seal names; the cost of the re-mint it forces is estimated, not measured.
  • The TOP is ours: its six rows are what this workflow needed, each scored from the tool's documentation, not from a run on this workload; on remote execution, ecosystem and scale the general build systems are far ahead.
